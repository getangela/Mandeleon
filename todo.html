    Self-service "Delete my account and avatar" Done, pending one live test Built (Sept 2026), directly motivated by a real gap this hit: deleting a user from the Netlify Identity dashboard only ever removed their login, never their data — the avatars, saved_tiles, board_tiles, and boards rows stayed behind as orphans, which is exactly what made the avatar name "AEON" unusable again after a round of Identity-dashboard cleanup even though no Identity user existed for it anymore. The one part not yet exercised against the live site: removing the Identity login uses the admin-scoped token Netlify's classic Functions+Identity integration is documented to expose via context.clientContext.identity — the same integration style context.clientContext.user already relies on successfully everywhere else in this project — but it's never actually been called for an admin operation like this before. If it works, the response comes back with loginRemoved: true and nothing further is needed. If that token isn't available for some reason, the account's data is still fully deleted either way (that part is tested and confirmed working); only the login itself would need one manual removal from the Identity dashboard, same single step as before this feature existed — so there's no failure mode where this makes things worse, only one where a rare manual cleanup is still needed. Verified with an automated test: the confirmation modal blocks on anything other than typing DELETE, the endpoint isn't called until confirmed, and a successful delete clears the avatar, the account-linked flag, and logs the visitor out.

    Fix decay firing on UTC-day rollover instead of the visitor's own day Done Real report (Sept 21): meters dropped from 70%+ to ~40% same-day, right after reopening the avatar panel following a login — looked exactly like a sync/overwrite bug, but wasn't. Root cause: todayStr() (used everywhere "today" is checked — decay, the daily feed caps, the streak) read toISOString(), which is UTC. UTC's date flips at a different clock time in every timezone (e.g. 7-8pm US Eastern) — so feeding an avatar in the evening and reopening the panel a couple of hours later, still the same evening for the visitor, could land after the UTC date had already ticked over, applying one full day's decay to every meter at once even though nothing that felt like "a day" had passed. Fixed by building the date string from the browser's local year/month/day instead, so "today" now matches the calendar day the visitor is actually experiencing. Confirmed the login/sync compare-before-overwrite logic itself was not at fault — it was never even reached in this scenario.
